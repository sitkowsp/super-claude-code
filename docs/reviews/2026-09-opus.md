# Architecture review — Opus — 2026-09-05

Reviewed: `DESIGN.md` v1.0 rev. 3.1 (sections 0–18), read in full.
Ground rule respected: section 0 decisions are treated as closed; where I attack one, I say so explicitly.

## Weaknesses

### 1. `never_share` is not a boundary — the shared `.git` directory defeats it (§6, §0 "Izolacja pracy" and "Sandbox", §4.1 rules 5–6)

Section 6 states that a worktree is created with `git worktree add` and then files matching `never_share` are deleted from the worktree — "they are in the repo, not in the executor's working copy" — while `.git` of the worktree points at the shared repository. That last clause destroys the guarantee the first clause makes. Any executor with a shell can recover every deleted file with one command against the shared object store (`git show HEAD:.env`, `git cat-file`, or simply reading `.git/objects` if the file was ever committed), and every CLI executor has a shell: Codex runs in a `workspace-write` sandbox that permits command execution (§5.4), Gemini runs in auto-accept mode (§5.3), Grok Build likewise (§5.5a). The design acknowledges the risk only halfway: §6 says the Ollama and claude-sub adapters block `git` hard, and §4.1 rule 5 forbids git use for everyone else — but a prompt rule is not an isolation mechanism, and blocking the literal string `git` does not block `cat .git/objects/...`, `python -c`, or any other read path. This matters far beyond hygiene: `privacy: local-only` (§6, §14.6 `local_only_paths`) is the control that lets NUCO data stay on srv-ai and is the basis of the `docs/privacy.md` NIS2 claim (§12, §13.2). Right now a `public` task routed to Codex sits in a directory from which company secrets are one command away, and the audit trail (`events.jsonl`) would not even record the read. The fix is architectural, not textual: either the executors get a *copy* of the tree rather than a git worktree (losing cheap diffing, which `git diff --no-index` or a scratch repo can replace), or the worktree gets its own shallow single-branch repository whose object store contains only the branch history with sensitive paths filtered. This should be decided in phase 1, before the first real dispatch, because it changes `worktree.py`, the merge path in §4.4, and the snapshot mechanism in §16.6.

### 2. The core contract is prompt-enforced for three of five executors, and `blocked` = hard kill collides with auto-commit (§3.3, §4.1, §5.1, §5.3–5.5, §10, §16.6)

The entire system rests on `REPORT.md` being written, overwritten (not appended), with valid front-matter, at the right moments, and on the executor *stopping* when it writes `blocked` (§0 "Komunikacja wykonawca→Claude", §3.3, §4.1 rule 3). Exactly one adapter can enforce any of this: Ollama, which owns its agent loop and exposes `write_report` as a tool that terminates the loop (§5.2). For Gemini, Codex and Grok Build the enforcement is a sentence in `AGENTS.md`/`GEMINI.md` plus the hope that a general-purpose coding agent, mid-task, will remember a file-writing convention it was told about once — and these three are precisely the first-choice executors for `implement`, `refactor`, `ui` and `test` (§14.4). The design's answers are detection, not enforcement: `report_invalid` twice in a row → `failed` and the planner avoids the model for that role (§10), and `council bench` scores protocol compliance and can set `enabled:false` (§16.2, phase 3). Taken together, the documented remedy for "a strong model does not follow our reporting convention" is to remove that model from the team the whole design is built around. Worse is the interaction between §3.3 ("`blocked` → the executor's process is terminated, it does not wait") and §16.6 (the watcher commits `git add -A` on every report). A CLI agent that writes `blocked` and keeps working — the overwhelmingly likely behaviour, since nothing makes it exit — is killed at an arbitrary moment, and the snapshot commit then captures a half-applied edit as the task's resume point. Phase 1 needs a per-adapter compliance shim (a wrapper prompt plus a post-run reconciliation pass that synthesises a `failed`/`done` report from the process exit and the worktree diff), and `blocked` needs a grace period with a report re-read before the kill, not `SIGKILL` on file-change.

### 3. The orchestrator is the serial bottleneck, and the design keeps adding to its load while claiming wall-clock division (§13.2, §14.4, §15.1, §15.2, §16.11)

The headline benefit in §13.2 is "wall-clock time ÷ number of executors", but §15.1 assigns Claude everything that cannot be cut cleanly — contracts, architecture decisions, integration, the glue layer, final review, merge, and all conversation with the human — and §14.4 makes `contract` a Claude-only role. In playbook A (§15.2), waves 1 and 3 are Claude alone, and Claude also reviews wave 4; only wave 2 is parallel. That is textbook Amdahl: if the serial fraction is half the epic, four executors buy at most ~1.6× regardless of how good the delegation machinery is, and nowhere in the document is that fraction estimated. The mitigations compound the problem rather than relieve it — context dieting, `HANDOFF.md` at `PreCompact`, quoted-only report bodies (§16.8, §16.11) all cost Claude tokens and attention, and every `blocked`, every `dissent` (§16.5), every `/council:inbox` item (§14.1 #14) routes back through the same single-threaded resource. §16.10 is the right instinct — measure solo vs council honestly — but it lands in phase 2, after the phase-1 stop-rule decision has already been made on feeling. The design should commit now to a per-playbook target for "Claude-serial minutes as a fraction of epic wall-clock", instrument it from phase 1 (the data is just `events.jsonl` timestamps plus who held the task), and treat any playbook above ~50 % as a planning bug in that playbook, not as a fact of life.

## Missing

**A concurrency and locking model for the shared git directory.** `TaskStore` gets a lock and the scheduler gets asyncio semaphores (§2), but git — the one resource genuinely shared by every moving part — gets none. At steady state the design has up to 3–4 executor worktrees active (§0, §14.6 `max_parallel: 4`), a watcher performing `git add -A && git commit` on every report from every task (§16.6, poll every 2 s), the integrator running speculative rebases of each finished branch onto `main` *and* onto every other ready branch of the wave in throwaway worktrees (§16.7), and the real rebase/`merge --no-ff` sequence during `/council:merge` (§4.4). All of these write to one `.git`: `index.lock` per worktree is separate, but `refs/`, `packed-refs`, the object store, `gc`/`prune` behaviour and worktree registration are not, and `git worktree remove` during `council_collect` races with anything else touching the administrative files. On Windows — the declared primary platform (§0) — this fails as intermittent `Unable to create '.../index.lock': File exists` and file-in-use errors during ref updates, which will surface as random `failed` tasks that `doctor --repair` (§13.1.9) cleans up without ever explaining. The document needs a section stating a single git serialisation discipline: one process-wide async lock around every git invocation that mutates the repository, snapshot commits batched or coalesced rather than fired per report, `gc.auto=0` on the target repo, and a documented ordering between watcher commits, speculative rebases and `council_collect`. This is cheap to write and impossible to retrofit calmly once three executors are running.

## Cut

**Grok `mode: pull` and the public `worker_*` HTTP transport (§0 "Grok" row — I am criticising a closed decision here; §5.5b, §12 `any-mcp-client.md`, §17 `SECURITY.md`).** This is the single largest cost-to-value item in the plan. It requires a second MCP transport, a bearer-token auth model, a Cloudflare tunnel dependency, a parallel file-access API (`worker_read/write/list/run/report`) that must re-implement every scope and `never_share` check the adapter path already implements — a second place for weakness 1 to reappear — a security policy and disclosure process because it is a publicly reachable endpoint with write access into the user's repository, plus its own documentation page. What it buys is explicitly degraded: 15-minute scheduling latency, one turn per invocation, no `blocked`→resume within a turn, `public` privacy only (§5.5b "Ograniczenia zaakceptowane"), for a provider that already has a working push adapter in `mode: cli`. The stated strategic justification — that the same transport lets any MCP client join the team — is real but speculative, and it is a v1.1 feature validated by demand, not a v1 requirement: nothing in the reference scenario (§7), in any of the ten playbooks (§15.3), or in the day-in-the-life narrative (§15.5) needs it. Cut `pull` and `both` from `council.json`, ship `mode: cli` only, and reclaim phase 3 for the things the stop rule actually depends on: documentation, `council bench`, and the honest solo-vs-council numbers.
