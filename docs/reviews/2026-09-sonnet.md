# Architecture review — Sonnet — 2026-09-05

## Weaknesses

**1. Scope/context isolation is a social contract enforced only for the two adapters the design itself controls (§3.2, §4.1.2, §5.1, §6).** Ollama and `claude-sub` get real technical enforcement: the tool functions (`read_file`/`write_file`/`run`) are implemented by the adapter and can literally refuse writes outside `scope` and reads of `never_share`. Codex, Gemini, and Grok CLI, however, run as full processes with their own filesystem access inside `cwd=worktree` — and a `git worktree` checkout contains the *entire* repository tree, not just `context_files`. The "only change files in scope" and "only read `context_files`" rules for these three executors live exclusively in the natural-language Charter (§4.1, points 2–3) rendered into `AGENTS.md`/`GEMINI.md`. Nothing in §5.3–5.5 stops Codex from reading `config/*.sql` that happens to sit in the same worktree, or from editing a file outside `scope` — that violation is caught only after the fact, at `/council:review` (§4.4), by diffing against the declared scope. For a design whose entire security story (§6) rests on `never_share` + scope discipline, having two-thirds of the executor fleet enforce this by *asking nicely* is a structural gap, not a minor rough edge. `never_share` file deletion from the worktree (§6, bullet 2) mitigates the worst case (secrets), but ordinary `internal`/`local-only` boundary violations for arbitrary non-`never_share` paths are not physically prevented for CLI-based executors at all.

**2. The plan is not actually in one place, despite the document's own premise (line 4: "this document is the only source of truth").** Section 8 states the original 4-phase, ~7-session plan. Then §13.4, §14.7, §15.6, and §16.16 each independently append work to phases 1–3, and none of them rewrites §8 itself — they only say "in addition to §8" or "overrides §8 and §13.4 where they differ" (§14.7's own header). By the end of the document, reconstructing "what is actually in Phase 2" requires manually merging four non-adjacent tables (§8, §13.4, §14.7, §16.16) scattered ~350 lines apart, several of which have overlapping and partially contradictory items (e.g., `/council:compare` is placed in Phase 3 by §13.4 then explicitly moved to Phase 2 by §15.6). This is exactly the kind of drift the document claims to forbid ("if implementation diverges from the document, the document gets fixed in the same commit," line 4) — except here the divergence is internal, between the design's own sections, before a single line of code exists.

**3. The quality/trust system has no ground-truth signal, only peer agreement.** `council bench` (§16.2) validates *protocol* compliance (does the model overwrite REPORT.md correctly, respect scope, avoid git) — not whether its actual engineering judgment is any good. `trust` (§16.1) escalates a model from `probation` to `standard`/`trusted` based on `review_ok` outcomes, where the reviewer is itself another delegated model (`grok`/`gemini`/`local`, per `by_role.review` in §3.1 and §14.4). Nothing establishes that the reviewer's judgment is calibrated against real bugs; two models can share correlated blind spots (e.g., neither flags a subtly wrong SQL join, or both accept a plausible-looking but wrong API contract), and the system reads that as confirmation, promoting the author to `trusted` and derisking future gates (§16.1: "trusted can merge chores without a gate"). `dissent` (§16.5) helps only when a model actively disagrees — it does nothing when two models are quietly, jointly wrong. The `stats`/solo-vs-council rachunek (§16.10) measures wall-clock and rework, not correctness, so it will not surface this failure mode either.

## Missing

There is no CI pipeline for the `council-mcp` project's own repository. Section 9 specifies local commands (`ruff`, `pytest -q`, `mypy` is even absent from the plugin's own lint rules — E,F,I,UP,B only, no type-checking rule for the very codebase that pydantic-types everything). Section 14.5's `gates` and §14.7's Phase-4 "CI (GitHub Actions/Gitea) running the same gates" both describe CI **for the target repo the plugin operates on**, never for `super-claude-code` itself. Given §17 commits to MIT + public GitHub from the start, with external contributors expected to send new adapters and playbooks (§17, "new model = one adapter file + a docs entry"), the absence of any described `.github/workflows/*.yml` running lint/type-check/tests on every PR to the plugin's own repo is a real gap — contributions could regress `council-mcp` with no automated gate at all before a human ever looks. This should have been part of Phase 0 or Phase 1 deliverables, not left implicit.

## Cut

Cut Grok `mode: pull` and the generic `worker_*` MCP transport (§5.5b, and its generalization to "any MCP client" in `docs/connect-models/any-mcp-client.md`, §12) from v1 scope entirely — not merely deferred to Phase 3 as currently planned, but dropped until real demand appears. I recognize §0 already closed this as "we build both variants, user chooses via `mode`," so this is a direct challenge to a closed decision. The justification: this is the single largest new attack surface in the whole design — a public HTTP/SSE endpoint behind a Cloudflare Tunnel, secured by one bearer token, that lets an external, un-probed, un-benched caller claim tasks and write files via `worker_write`/`worker_run` (§5.5b) — and it is being built to satisfy a capability ("any MCP client can join the team, ChatGPT, Cursor, a second Claude") that no scenario in §7 or §13.2 actually exercises; it is speculative generality bolted onto a system whose own stop-rule philosophy (§8, §15.1) says "don't build what isn't earning its keep." The CLI path (`mode: cli`) already gives Grok parity with Codex/Gemini for v1's real use cases. Pull-mode security hardening (rotation, rate limiting, per-caller logging beyond a single token) is also unspecified, which compounds the risk of shipping it early.

## Builder's perspective (8 sessions)

Section 8's literal phase table sums to 7 sessions (1+2+2+2), and even that base scope is close to right-sized for what §8 *originally* asked for — Phase 0's single session for `council_models`/`council_ask`/one Ollama adapter/probe is realistic, and is the one part of the plan that is not underestimated, precisely because it deliberately excludes worktrees, dispatch, and multi-adapter orchestration.

Everything past Phase 0 is severely underestimated once §13–16 are taken into account, because those sections are literally three more design-review passes that each append substantial new subsystems onto the *same* two-session buckets without ever revising the session counts. Concretely, "Phase 2 (2 sessions)" as amended by §14.7, §15.6, and §16.16 combined must now deliver: DAG/wave scheduling with dependency-aware unlocking, the `contract`/`frozen` role and cross-task contract propagation, deterministic language-specific `gates` plus their `gates.json` reporting, `council_repo_map` via tree-sitter/ctags with caching, epic tracking (`epics/<id>.json`, `/council:epic`), rate-limit cooldown/fallback routing, `council_plan_validate` size limits, `/council:inbox`, skill wiring for three subagents, the entire playbook engine plus at least three playbooks (`feature`, `bug-hunt`, `data-internal`) and playbook-selection logic, `trust`/probation state machine, the cheap-model brief pre-check, the `adversary` role, `dissent` handling, background merge-preview rebasing, `/council:why`, solo-vs-council cost estimation, and `LESSONS.md` generation. Any one of these (DAG scheduling, or the playbook engine, or the trust state machine) is plausibly a full session on its own; together they are easily 4–6 sessions of work, not the roughly-one-extra-session that "2 sessions, plus this list" implies. Phase 3 has the same problem in miniature: bilingual documentation for twelve separate files (§12) is bundled into the same two sessions as `council_recall`/pgvector integration, Docker-based per-task environments, Playwright/Context7 wiring for executors, `council bench`, `council night`, team profiles, and `council report` — any single item here (writing and validating twelve genuinely good user-facing docs, or standing up pgvector-backed semantic recall) is a multi-day task by itself. The document's own iterative self-critique is the root cause: each of §13, §14, §15, §16 was written as "what's missing," found real gaps, and fixed them by adding scope — but never went back to §8 and re-costed the phases, so the session estimates that a builder would actually plan against are frozen at the pre-critique, minimal-v1 sizing while the feature list tripled. A builder working from §8 alone would be pleasantly surprised for one session and then routinely miss every subsequent phase's session budget by 2–3x unless they explicitly re-scope Phases 1–3 before starting, most likely by pushing everything from §14 onward (contracts, gates, epics, trust, playbooks, adversary/dissent, recall, bench/night/profiles) into new, separately-numbered phases 4 through 7+, which is the honest read of "8 sessions" for what this document actually now specifies.
